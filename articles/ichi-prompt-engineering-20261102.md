AIとの対話が当たり前になった今、**プロンプトエンジニアリング**はエンジニアにとって欠かせないスキルになっています。私自身、GPT-4やClaude、Geminiといったモデルを日常的に使う中で、「同じ質問でもプロンプトの書き方一つでアウトプットがまったく変わる」という体験を何度もしてきました。この記事では、その経験をもとに、プロンプトエンジニアリングの基礎から実践テクニックまでを体系的に紹介します。

## プロンプトエンジニアリングとは何か

プロンプトエンジニアリングとは、LLM（大規模言語モデル）に対して**意図した出力を得るための入力文（プロンプト）を設計・最適化する技術**です。コーディングのようにコンパイラが厳密にルールを解釈するわけではなく、モデルの「確率的な次トークン予測」という性質を理解した上で、文脈・制約・例示などを組み合わせて誘導します。

単に「質問をうまく書く」という話ではなく、モデルの内部動作への理解、反復的な実験、そして体系的な評価が求められます。プロンプトは一種のAPIインターフェースであり、エンジニアリングとして扱うべき領域です。

## 基本テクニック：ゼロショット・フューショット・CoT

### ゼロショットプロンプト

最もシンプルな形式で、例を与えずに直接タスクを指示します。モデルの事前学習知識に依存するため、汎用的なタスクに向いています。

```text
あなたは経験豊富なコードレビュアーです。
以下のPythonコードのバグを特定し、修正案を提示してください。

def divide(a, b):
    return a / b

result = divide(10, 0)
print(result)
```

このようにロールを明示することで、モデルは「コードレビュアー」として振る舞い、`ZeroDivisionError`への対処やガード節の追加といった具体的な提案を返してくれます。

### フューショットプロンプト

いくつかの入出力例を見せることで、モデルに期待するフォーマットや推論パターンを学ばせます。分類・変換・抽出など、出力形式が明確なタスクで特に威力を発揮します。

```text
テキストの感情を「positive」「negative」「neutral」に分類してください。

入力: 今日のリリースは完璧でした！
出力: positive

入力: ドキュメントが古くて使い物にならない。
出力: negative

入力: プルリクエストを送りました。
出力: neutral

入力: このAPIのレスポンスが遅すぎて開発が止まっています。
出力:
```

例を3〜5個程度提示するだけで、ゼロショットでは曖昧になりがちな境界ケースの判定精度が大幅に上がります。

### Chain-of-Thought（CoT）プロンプト

複雑な推論タスクには、「ステップバイステップで考えてください」という一言を加えるCoTが有効です。モデルに中間推論プロセスを出力させることで、最終的な答えの精度が向上します。これはGoogleの研究で実証されており、数学的問題解決やコードデバッグで顕著な効果があります。

```text
以下のシステムで発生しているパフォーマンス問題を診断してください。
ステップバイステップで原因を分析し、優先度の高い改善策を提案してください。

【状況】
- Webアプリのレスポンスタイムが平均3秒を超えている
- データベースへのクエリ数がリクエストあたり50件以上
- キャッシュ層は存在しない
- ユーザー数は過去3ヶ月で10倍に増加
```

「ステップバイステップで」という指示があるだけで、N+1問題の特定、インデックス設計、キャッシュ導入の優先順位付けまで、論理的に整理されたアドバイスが返ってきます。

## 実践的な設計原則

プロンプトの品質を高めるために、私が日常的に意識している原則をまとめます。

**① 役割・文脈・タスク・制約をセットで与える**
「あなたは〜です（役割）。背景として〜があります（文脈）。〜してください（タスク）。ただし〜は除外します（制約）」という構造が基本です。

**② 出力フォーマットを明示する**
「JSON形式で」「箇条書きで3点」「200字以内で」といった形式指定は、後処理の自動化にも直結します。特にシステムプロンプトとして設定できる環境では、フォーマット指定を固定しておくと安定性が増します。

**③ ネガティブプロンプトより肯定的な指示を使う**
「〜しないでください」より「〜してください」のほうがモデルは安定して従います。「専門用語を使わないでください」より「中学生でも理解できる言葉で説明してください」のほうが意図した結果を得やすいです。

**④ プロンプトをバージョン管理する**
プロンプトはコードと同様に変更の履歴が重要です。私はGitリポジトリでMarkdownファイルとして管理し、モデルのバージョンアップ時の挙動変化もコミットログで追えるようにしています。

## システムプロンプトとユーザープロンプトの使い分け

OpenAI APIなどのインターフェースでは、メッセージはロールによって構造化されています。この使い分けが、本番システムでの安定性に大きく影響します。

- **systemロール**: モデルの振る舞いの基本設定。ペルソナ、出力形式、制約事項を記述。変更頻度が低い固定的な指示。
- **userロール**: エンドユーザーからの動的な入力。タスクの具体的な内容。
- **assistantロール**: モデルの過去の応答。フューショット例をここに書くことも可能。

フューショット例をsystem/user/assistantのやり取りとして構造化すると、単純にsystemプロンプトに書くより精度が上がるケースがあります。特に「会話のトーンや文体を真似させたい」場面では有効です。

また、**プロンプトインジェクション攻撃**への対策も本番では必須です。ユーザー入力をそのままプロンプトに埋め込む設計は危険で、入力のサニタイズや、systemとuserを明確に分離する設計が求められます。

## まとめ

プロンプトエンジニアリングは、LLMを単なるチャットボットとしてではなく、**プログラマブルな推論エンジン**として活用するための技術です。この記事で紹介したポイントを改めて整理すると：

- **ゼロショット・フューショット・CoT**を使い分けてタスクに最適なアプローチを選ぶ
- **役割・文脈・タスク・制約・フォーマット**をセットで設計する
- **system/user/assistantロール**を意識してプロンプトを構造化する
- プロンプトをコードと同様に**バージョン管理・評価・改善**するサイクルを回す

LLMは日々進化していますが、「意図を正確に伝える技術」の重要性はモデルが変わっても本質的には変わりません。プロンプトエンジニアリングのスキルは、AI時代のエンジニアにとって長期的に価値ある投資だと私は考えています。ぜひ自分のワークフローに取り入れて、AIとの協働を一段上のレベルに引き上げてみてください。

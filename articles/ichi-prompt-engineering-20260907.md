AIと会話していると「なんでこんな答えが返ってくるんだ」と頭を抱えた経験、誰しも一度はあるんじゃないかと思います。私も最初はそうでした。でも、プロンプトの書き方を少し工夫するだけで、AIの出力品質は劇的に変わります。この記事では、私が実際の開発・執筆業務で使っている**プロンプトエンジニアリング**の技術を体系的にまとめました。

## プロンプトエンジニアリングとは何か

プロンプトエンジニアリングとは、LLM（大規模言語モデル）に対して意図した出力を得るために、入力テキスト（プロンプト）を設計・最適化する技術のことです。

単なる「質問の仕方」と軽く見られがちですが、実際には以下のような要素が絡み合う、れっきとしたエンジニアリング領域です。

- モデルの学習方法・トークン処理への理解
- 認知科学・言語学的な知識
- 反復的な実験と評価

特にGPT-4やClaude 3といった高性能モデルが普及した現在、プロンプトの質がそのままプロダクトの品質に直結するケースが増えています。

## 基本テクニック：構造化されたプロンプトを書く

良いプロンプトには**役割・文脈・指示・制約**という4つの要素が揃っています。

### ロール・プロンプティング

AIに特定の役割を与えることで、その文脈に最適化された回答を引き出せます。

```
# 悪い例
Pythonのコードをレビューして。

# 良い例
あなたはPythonのシニアエンジニアです。
以下のコードを、パフォーマンスとセキュリティの観点でレビューし、
具体的な改善提案を箇条書きで提示してください。

```python
def get_user(user_id):
    query = f"SELECT * FROM users WHERE id = {user_id}"
    return db.execute(query)
```
```

「良い例」では役割・観点・出力形式を明示しています。これだけでSQLインジェクションのリスクや`SELECT *`の非効率性といった具体的な指摘が返ってくるようになります。

### Few-Shotプロンプティング

モデルに例を見せることで、期待する出力フォーマットや品質を学習させる手法です。

```
以下の形式でコミットメッセージを生成してください。

例1:
変更内容: ユーザー認証にJWTを追加した
出力: feat(auth): implement JWT-based user authentication

例2:
変更内容: ログイン時のバリデーションエラーを修正した
出力: fix(auth): resolve validation error on login form

それでは、以下の変更内容でコミットメッセージを生成してください。
変更内容: 商品一覧APIのレスポンス速度を改善するためにキャッシュを導入した
```

Few-Shotは出力の**一貫性とフォーマット統一**に絶大な効果があります。特にチームで使い回すプロンプトを設計するときに欠かせないテクニックです。

## 応用テクニック：思考の質を高める

基本を押さえたら、次は出力の**論理品質**を高める手法に踏み込みましょう。

### Chain-of-Thought（CoT）プロンプティング

複雑な問題を解くとき、モデルに「考えるプロセス」を明示させることで精度が上がります。

```
次の問題をステップバイステップで解いてください。

問題:
あるECサイトで、商品Aの原価は800円、定価は1200円です。
20%引きセールを実施した場合、利益率は何%になりますか？

手順:
1. セール価格を計算する
2. 利益額を計算する
3. 利益率を計算する
4. 最終的な答えを明示する
```

「ステップバイステップで」と指示するだけでも精度は上がりますが、こうして具体的な手順を書き出すと、モデルが途中で論理を飛躍させるミスを防げます。私の経験では、数値計算や条件分岐が絡む問題でCoTを使うと、エラー率が体感で半分以下になります。

### Self-Consistency（自己一貫性）

同じプロンプトで複数回出力を生成し、最も一貫した答えを採用する手法です。APIを使ってバッチ処理するケースで特に有効です。重要な判断を伴うタスク（バグの原因分析、セキュリティ診断など）では、1回の出力を鵜呑みにせず複数回試すことを習慣にしています。

## プロダクションで使えるプロンプト設計のベストプラクティス

実際のアプリケーションにプロンプトを組み込む際に、私が意識しているポイントを整理します。

### 制約とフォーマットを明示する

出力がシステムの入力になる場合、フォーマットの乱れは致命的なバグになります。

```
以下のユーザーレビューを分析し、必ず以下のJSONフォーマットで出力してください。
他の文章は一切含めないこと。

レビュー: 「配送が遅かったけど、商品自体はとても満足しています！また買います。」

出力フォーマット:
{
  "sentiment": "positive" | "negative" | "mixed",
  "score": 1〜5の整数,
  "key_points": ["ポイント1", "ポイント2"],
  "repurchase_intent": true | false
}
```

`他の文章は一切含めないこと` という一文が地味に重要です。これがないと「以下がJSON出力です:」のような前置きが入り、JSONパースが壊れます。

### プロンプトのバージョン管理をする

プロンプトはコードと同じようにバージョン管理すべきです。私のチームでは以下のような運用をしています。

- プロンプトをYAMLまたはMarkdownファイルとしてGitで管理
- 変更のたびにA/Bテストで品質を比較評価
- モデルのバージョンとプロンプトのバージョンをセットで記録

プロンプトは「書いたら終わり」ではなく、継続的に改善するアーティファクトです。

### トークン効率を意識する

APIコストと応答速度に直結するため、不要な冗長表現は削ぎ落とします。ただし、削りすぎると精度が下がるトレードオフがあるので、ベンチマークを取りながら最適なバランスを探ることが大切です。

## まとめ

プロンプトエンジニアリングの要点を振り返ります。

| テクニック | 効果 | 使いどころ |
|---|---|---|
| ロール・プロンプティング | 専門性の向上 | レビュー・分析タスク |
| Few-Shot | フォーマット統一 | 繰り返しタスク・API連携 |
| Chain-of-Thought | 論理精度の向上 | 計算・推論問題 |
| 制約の明示 | 出力の安定化 | プロダクション組み込み |

プロンプトエンジニアリングは「センス」の話ではなく、再現性のある**エンジニアリング**です。構造を理解し、実験を繰り返し、バージョン管理する——この姿勢を持つだけで、AIとの協働の質は一段階上がります。

まずは手元のプロンプト一つを、この記事の型に当てはめて書き直してみてください。変化を実感するのに、それほど時間はかからないはずです。
